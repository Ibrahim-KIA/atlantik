# Security boundaries and release review

PostgreSQL runtime roles are NOSUPERUSER/NOBYPASSRLS and do not own tables. Startup rejects migration/owner/superuser credentials. The API cannot read queued encrypted email bodies or signing credentials outside the relevant tenant APIs; the worker has a separate role for durable delivery. Use separate credentials and databases per environment. Role provisioning is idempotent and is run only by migrations.

Organization and tenant-owned tables use forced RLS with transaction-local tenant context. Tenant-aware composite foreign keys prevent cross-tenant team/member/workspace links. Context is reset by commit/rollback before a pooled connection is reused. Organization row locks serialize quota, membership and resource mutations. Global identity tables are deliberately outside tenant RLS; endpoints must authorize global identity access using a live session. Platform organization functions independently authenticate administrator sessions and return only metadata. Platform permissions never imply tenant membership.

Passwords use asynchronous scrypt (N=65536, r=8, p=2; random 256-bit salt). Sessions, verification/reset/invitation tokens and API keys are random 256-bit opaque secrets stored as SHA-256 digests. A shared AES-256-GCM key encrypts sensitive outbox payloads and webhook signing secrets with unique nonces. Completed jobs erase their payload. Backups and encryption keys must be protected separately. Key rotation currently requires an operator-led re-encryption migration; do not replace the key while pending jobs or stored webhook secrets still depend on it.

Redis atomic expiring counters protect registration, login, reset, verification, sessions and authenticated clients; normalized account digests supplement IP login limits. Redis outages fail closed. Trust forwarded client addresses only from explicitly configured proxy CIDRs. The default trusts none; configure the CIDR for your controlled ingress to avoid all external traffic sharing a proxy IP quota. HTTPS must terminate at a controlled production ingress. CORS is not enabled by default.

Strict input objects reject mass-assigned fields; UUID identifiers and string lengths are validated. SQL values use parameters; the only SQL identifiers are fixed migration/provisioning constants. Errors are sanitized and request IDs correlate HTTP, structured logs and audit records. Pino serializers exclude query strings, credentials, request bodies and headers. Audits record authenticated action failures as well as successful mutations. Database administrators can still alter data; append-only application logs do not replace immutable external audit storage.

Webhooks require HTTPS hostnames, port 443, no embedded credentials and IPv4 public destinations. Every attempt resolves and validates DNS, pins the selected address while preserving hostname/TLS verification, refuses redirects and enforces DNS/request timeouts. Private, loopback, link-local, multicast, carrier NAT and IPv6 destinations are rejected. Apply an outbound network deny policy for private/metadata ranges as defense in depth. Signature verification uses constant-time comparison, exact request bytes and a five-minute window.

Automated acceptance covers cross-tenant HTTP and direct-SQL reads/writes, ID manipulation, escalation, owner protection, scoped/expired/rotated credentials, single-use tokens, quotas under concurrency, duplicate/stale billing events, queue retries, SSRF rules and real dependency outages. See [progress](progress.md) for executed checks. Production release additionally requires load/brute-force review, external penetration testing, identity recovery procedures, least-privilege secret distribution, backup restoration and staging sign-off. MFA/SSO, external tracing and a payment-provider-specific adapter are extensions, not claimed deliverables of this foundation.
